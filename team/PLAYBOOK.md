# Команда агентов Claude Code: роли и процесс

Как устроить работу команды из нескольких сессий Claude Code над одним проектом. Каждая роль — отдельная постоянная сессия (чат) в приложении Claude. Владелец проекта общается в основном с одной сессией — General Manager.

## Роли

| Роль | Модель | Усилие | За что отвечает | Чего не делает |
|---|---|---|---|---|
| General Manager | Opus | high | План работ, порядок задач, решения уровня плана, споры после двух возвратов, отчёты владельцу каждый час | Сам задачи не исполняет |
| Manager | Sonnet | medium | Выдаёт задачи по порядку, ведёт статусы в плане и журнал передач | Не меняет план, не спрашивает владельца |
| Senior Developer | Opus | high | Сложный код: новые модули, архитектурно важные изменения; ведёт агентов-писателей | Не берёт следующую задачу сам |
| Middle Developer | Sonnet | medium | Простой код: запуск готового, переносы, загрузки, массовые однотипные правки | Не трогает ядро без выдачи |
| Architect | Opus | high | Описания задач для разработчиков: что строим, правила, критерии приёмки | Кода не пишет |
| Auditor | Opus | high | Принимает каждую задачу: проверяет сам, по данным и коду, а не по отчёту исполнителя | Не чинит, не ставит «сделано» |
| Head of Security | Opus | high | Новые права и настройки защиты, проверка нового кода и агентов с доступом к командам, выход в интернет, решение что удалять, журнал решений по безопасности | Рутину отдаёт DevOps |
| DevOps | Sonnet | medium | Рутина безопасности: сверка контрольных сумм, бэкапы, запуск одобренной чистки, команды установки по одобренному | Не выносит вердиктов по безопасности |
| Analyst | Sonnet | high | Проверяет тексты и результаты на соответствие исходным данным; готовит вопросы владельцу | Спрашивает владельца только с разрешения GM |
| Releaser | Haiku | low | Записывает версии в локальный git после каждой принятой задачи | Больше ничего |

Правило выбора модели: проверяющий не слабее того, кого проверяет; рутина — на Sonnet или Haiku; Opus — там, где ошибка дорого стоит.

### Агенты-писатели (без своих сессий)

Для массовой однотипной работы (например, сотни однотипных заданий) — встроенные агенты Claude Code (`.claude/agents/*.md`, модель прописана в файле). Разработчик вызывает такого агента на одно задание; агент стартует с чистого листа и закрывается. Это намного дешевле, чем держать отдельную сессию.

| Агент | Модель | Что делает |
|---|---|---|
| writer-senior | Opus | Сложное: сводные тексты, противоречивые случаи |
| writer | Sonnet | Основной объём |
| writer-junior | Haiku | Простое по шаблону; если сложнее — возвращает «нужен writer» |

У агентов-писателей нет инструмента запуска других агентов; пишут только в свою папку; каждый запуск — строка в общем реестре агентов с расходом токенов.

## Цикл задачи

1. **Manager выдаёт** задачу исполнителю — одним сообщением.
2. **Исполнитель делает** и сдаёт **сам** проверяющему, одним сообщением: что сделано, команды, цифры, изменённые файлы с контрольными суммами.
3. **Проверяющий** (Auditor; для текстов — Analyst; для безопасности — Head of Security) проверяет сам по данным: пересчитывает ключевые цифры, берёт случайную выборку, смотрит, что ничего не сломано и не утекло, что результат повторяется.
4. Вердикт: **ПРИНЯТО** → Manager ставит «сделано» и выдаёт следующую; **ВОЗВРАТ** → исполнителю, со списком дефектов.
5. **Два возврата максимум.** Если третья сдача снова не проходит — вердикт **СПОР**, его решает General Manager (принять с оговорками, сузить требования, сменить исполнителя) или выносит владельцу.
6. **Releaser** записывает версию в git. Код и настройки — только с «да» Head of Security.

## План

- Один файл плана. Сверху короткая таблица: №, задача в 3–6 слов, ответственный, статус значком, проверка значком. Ниже — подробности по каждой задаче.
- **Один ответственный и один проверяющий на задачу.** Два исполнителя — две задачи.
- **Строго по порядку:** в работе одна задача, следующая начинается только после приёмки предыдущей. Разработчиков двое, но работает в любой момент один — чтобы не перезаписать код друг друга.
- Значки: ✅ сделано · ⏳ в работе · ⬜ ждёт · ⏸ пауза до очереди · ↩ возвращено.
- В тексте для владельца — названия задач, а не номера.
- **Двигатель плана:** у General Manager будильник каждые 15 минут — если задача принята, сразу выдаёт следующую; если исполнитель молчит больше 30 минут — спрашивает статус. План не стоит, пока владелец не пишет.

## Кто кому пишет при проблеме

| Роль | Пишет при проблеме |
|---|---|
| Developer (оба), Architect, Analyst | Manager; права и доступ — DevOps |
| DevOps, Releaser | Head of Security |
| Auditor | ВОЗВРАТ — исполнителю, ПРИНЯТО — Manager, СПОР — General Manager |
| Manager, Head of Security | General Manager |
| General Manager | Владельцу |

Правила:
- **Проблема — сразу сообщением наверх.** Проблема: не хватает прав, команда не прошла, неясно задание, нужен чужой ответ, найдена ошибка, работа стоит больше 10 минут. Запись только в журнал — нарушение.
- Нет ответа 15 минут — на ступень выше.
- Владельцу напрямую пишут только General Manager и Head of Security (когда нужны права).
- Справочник команды — файл с адресом сессии каждой роли (`session_id`) и колонкой «кому писать». Сообщения между сессиями — инструмент отправки сообщения в другую сессию.

## Экономия токенов

- **Молчащая сессия ничего не стоит.** Деньги уходят на пробуждения: каждое сообщение будит сессию, и она перечитывает весь свой разговор.
- **Сообщение — только с задачей, возвратом, вопросом или проблемой.** «Принято», «к сведению», подтверждения — строкой в журнал.
- **Одно событие — одно сообщение одному адресату.**
- **Очистка разговора после принятой задачи** у ролей, которые часто просыпаются (оба Developer, Auditor, DevOps, Releaser; Manager — раз в день). Перед очисткой роль пишет памятку `MEMO-<роль>.md` (3–5 строк: на чём остановилась, что ждёт, что важно) и строку в журнал; следующую задачу начинает с памятки, описания роли и навыка. Не очищают: General Manager (нужна история решений владельца), Head of Security (история решений по безопасности), Architect, Analyst.
- **Агенты-писатели вместо длинных сессий** для массовой работы; перед большой волной — проба на пяти заданиях с замером расхода.

## Пауза рассылки

Приложение Claude ставит рассылку сессии на паузу после нескольких отправок подряд без сообщения владельца («Paused until your user's next message»). Обход: **ход по собственному будильнику снимает паузу.** У ролей, которые много пишут (Manager, Auditor), — повторяющийся будильник каждые 20–30 минут: отправить накопленное из `OUTBOX-<роль>.md`; если пусто — закончить ход одной строкой. Будильники живут, пока открыта сессия (до 7 дней) — после перезапуска ставятся заново.

## Знание роли — в файлах, не в памяти чата

- `roles/<роль>.md` — описание роли: отвечает за, не делает, кому пишет.
- **Навык на каждую роль** (`.claude/skills/<навык>/SKILL.md`): методика работы — чек-лист приёмки у Auditor, проверка диффов у Head of Security, формат плана и отчёта у General Manager, команды у разработчиков. Навыки и агенты лежат в защищённой папке: их пишет GM, проверяет Head of Security, ставит владелец одной командой с проверкой контрольной суммы.
- Журнал передач: `время | от → кому | задача | что | где | статус` — каждая передача.
- Журнал решений по безопасности — у Head of Security.
- **История разговоров:** журналы всех сессий на диске пересобираются скриптом в читаемый вид по ролям; ключи, пароли, токены, номера карт, IP и все значения из файла с секретами маскируются; если файл с секретами не читается — скрипт останавливается.

## Права и безопасность

- Владелец не нажимает окна разрешений. Нужные права Head of Security запрашивает у него одной командой на класс задач, с объяснением: что даёт, чем ограничено, как откатить.
- Опасные действия — через обёртки с жёстко заданной командой (запись версии, перенос в Корзину, выход в интернет по списку). Обёртку запускают только голой строкой, без `cd`, `&&` и перенаправлений.
- Удаление — только Head of Security и только в Корзину.
- Git локальный, никуда не публикуется. Секреты не попадают ни в git, ни в рабочие файлы.
- Выход в интернет — один раз по утверждённому списку с контрольными суммами.

## Порядок работы владельца

- Пишет только General Manager. Получает отчёт каждый час ровно в :00: что сделано, что в работе, что нужно от него.
- Новая роль: владелец создаёт сессию и называет её; General Manager пишет описание роли, ставит модель, вводит в работу (что прочитать, кому писать, первая задача).
- Названия всех файлов и папок — по-английски; содержание — на языке владельца.
